## Context

Relay currently assumes a single tenant per deployment: endpoints, events, and deliveries share one database without a tenant dimension.

This issue is a design RFC, not an implementation.

## Deliverable

Write `docs/rfcs/0001-multi-tenant.md` covering:

1. **Isolation model** — Compare shared collections with `tenant_id` and compound indexes, database-per-tenant, collection-per-tenant, and hybrid approaches. Recommend and justify one.
2. **Authentication** — Explain API-key-to-tenant mapping, JWT claims, and whether tenant identity belongs in a path, header, or API key.
3. **Migration** — Explain how an existing single-tenant deployment becomes tenant-0 and whether a migration script is required.
4. **Query impact** — Identify queries that need tenant filters and those affected by index changes.
5. **Security boundaries** — Explain how cross-tenant data access is prevented and how tenant context is propagated through handlers, workers, retries, and event replay.
6. **Operational impact** — Discuss backups, retention, observability, tenant deletion, and noisy-neighbor risks.
7. **Rollout plan** — Propose incremental phases with backward compatibility and rollback considerations.

## Acceptance Criteria

- [ ] RFC documents and compares the isolation strategies.
- [ ] One approach is recommended with explicit trade-offs.
- [ ] Authentication and tenant-resolution flows are documented.
- [ ] Migration from the existing single-tenant model is addressed.
- [ ] Affected data models, queries, and indexes are identified.
- [ ] Cross-tenant isolation risks and mitigations are documented.
- [ ] Worker and retry behavior is covered.
- [ ] Rollout and rollback strategy is included.
- [ ] No production implementation is included in this issue.

## Validation

Review the RFC against the current MongoDB models, indexes, API-key authentication, handlers, and delivery workers.

Ensure every recommendation is grounded in the current architecture and clearly distinguish decisions from open questions.
